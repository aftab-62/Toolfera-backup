# Local document processing

Tool definitions, URL availability, content, related links and SEO remain centralized in `lib/tool-definitions.ts`, `lib/catalog.ts` and `lib/additional-tool-content.ts`. New tools use the existing category/tool templates and lazy interface boundary.

## PDF to Word

`pdf-to-word.ts` extracts page text and image operators sequentially. Images are reduced to their document-sized placement at up to 150 DPI, 1.5 million output pixels and 1,600 pixels per side. The path supports bounded RGB, RGBA and one-bit sampling as well as decoded bitmap scaling. Image canvases and PDF pages are released after use; compressed images are capped at 24 MB. Text/layout reconstruction and OOXML packaging remain native editable content.

Pages with image operators and insufficient extractable text are marked for optional OCR before embedded images are collected. OCR is a separate user action, so its assets do not load for normal text PDFs.

## OCR

`pdf-ocr.ts` owns a Tesseract.js 7 Worker from construction, including initialization and language loading. Every protocol request has a tracked promise. Abort terminates the Worker immediately and rejects pending jobs. PDF render tasks, page canvases and the PDF loading task have matching cancellation/cleanup paths.

Versioned same-origin assets live in `public/_ocr/v7`. Only English is offered. Normal, SIMD and relaxed-SIMD LSTM cores are vendored because the pinned worker selects the compatible variant; only one is loaded. No source PDF/image data is sent to a service. Language data uses `cacheMethod: none` so no IndexedDB file or language cache is introduced.

Mobile OCR: five scanned pages, 5 MB and 1.8 million rendered pixels per page. Desktop: ten scanned pages, 10 MB and three million pixels per page. Pages are recognized in sequence, with actual engine progress. Unreadable scans fail instead of creating an empty document. Recognition and geometry reconstruction need human review.

## Word to PDF

The tool accepts DOCX, not legacy DOC. A worker reads a filtered ZIP with entry, XML, part and total expanded-byte caps. `word-docx-parser.ts` uses the browser DOMParser, rejects DTD/entity declarations, bounds text and yields between batches. It reconstructs supported headings, formatting, lists, PNG/JPEG images, page breaks and basic tables; unsupported features produce warnings.

`word-pdf.worker.ts` loads embedded Liberation Sans fonts only for conversion and calls the native pdf-lib/fontkit renderer. Text remains selectable. The renderer wraps paragraphs and table cells, paginates within a 100-page limit, guards oversized rows and caps the generated PDF at 40 MB. Fonts, complex Word layouts and unsupported glyphs can differ from the original. Worker termination provides immediate cancellation for archive reading or rendering.

The font and OCR distributions include their upstream license notices. No application database, file upload endpoint, external conversion API or user-file persistence is involved.

## Verification

Generate owned fixtures with `scripts/create-document-update-fixtures.py`. Existing `scripts/create-pdf-qa-fixtures.py` supplies the structured PDF/raster regressions. Run TypeScript, production build, the existing tool engine scripts, `verify-document-update.mjs`, `verify-browser-ocr.mjs`, `audit-production.mjs` and `measure-client.mjs` through the project's `scripts/sites-env.sh` runtime.

The OCR verification script adapts the same pinned protocol to a Node worker solely to inspect generated bytes. Browser QA also exercises the actual Web Worker independently. Runtime DOMParser/canvas substitutes in the verification scripts are development dependencies only.
